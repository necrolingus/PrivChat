## Functional Requirements

### 1. User Identity & Authentication
- **12-Word Identity Phrase**: When a user visits the application, they can choose between "I'm New" or "Returning User".
  - If new, the app generates a random 12-word seed phrase selected from the standard BIP-39 2,048-word dictionary ($2^{132}$ entropy combinations).
  - Returning users enter their 12-word phrase to unlock their cryptographic identity and device identity.
  - Losing the 12-word phrase results in permanent loss of identity and channel access keys.
- **Client Device ID & Server-Side Profile Persistence**:
  - Each device derives a unique, non-identifiable Device UUID client-side from the 12-word seed (no MAC, IP, or geo-location tracking).
  - Custom friendly display names are saved server-side per `deviceId` (`tbl_chatapp_profiles`) and automatically restored when returning users log in.
- **Session Persistence Control**:
  - Users can select their session security preference on login:
    - **Remember me on this device (7-day persistence)**: Saved in `localStorage`.
    - **Session only (expires on browser close)**: Saved in `sessionStorage`.

### 2. Channel Creation & Access Control
- **6-Word Channel Key**: Channels are identified and encrypted via a 6-word phrase key selected from the BIP-39 dictionary.
- **Standardized UI Terminology**: All UI elements strictly use uniform terminology: **12-Word Identity Phrase**, **6-Word Channel Key**, and **One-Time Invite PIN**.
- **Auto-Generated & Custom One-Time Invite PINs**:
  - Creating a new channel auto-populates an initial **One-Time Invite PIN** (`INV-XXXXXX`) while supporting custom PIN entries (e.g. `tester123`).
  - Joining an existing channel requires entering the 6-word channel key AND a valid **One-Time Invite PIN** generated by the channel owner.
- **Global OTP Non-Reuse Security Hardening**:
  - Once used, the invite PIN is permanently marked as consumed in PostgreSQL (`is_used = true`).
  - Consumed OTPs can NEVER be reused or reactivated by channel owners or kicked members under new identities.
- **Interactive Notification Center**:
  - Replaces intrusive modals with a header Notification Bell (`#btn-notification-bell`) and real-time unread badge counter (`#notification-unread-badge`).
  - Clicking the bell opens a dropdown popover displaying join requests with inline **Approve** and **Deny** buttons, kick/leave alerts, and action status notifications.
- **Owner Join Approval Queue**:
  - Channels default to "Owner Approval Required".
  - Non-owner joiners enter a `pending` state until the channel owner explicitly approves their join request.
  - `pending` users are strictly blocked from fetching chat history or receiving real-time socket broadcasts.
- **Owner Channel Closure & Deletion**:
  - When a channel owner leaves or closes a channel, the channel is permanently deleted from the database.
  - All stored historical ciphertexts and member records are cascaded and wiped.
  - Connected members receive a real-time "Channel closed" notification and return to the dashboard.
- **Dashboard Emergency Leave / Closure**:
  - Users can leave or close any active channel directly from their Dashboard without needing to re-enter the 6-word channel key.
- **Kicked & Left Member Access Prohibition**:
  - Once a user leaves or is kicked from a channel, they are permanently prohibited from re-joining or querying historical messages.

### 3. End-to-End Encryption & Messaging
- **Client-Side E2EE & Fixed Height Layout**: All text messages and photo uploads are encrypted client-side using Web Crypto API (`AES-256-GCM` + 12-byte random IV) prior to transmission. The chat window maintains a stable fixed-height container area (`85vh` / `720px`).
- **Digital Signatures (Impersonation Protection)**:
  - Every device derives an **ECDSA (P-256)** digital signing keypair client-side.
  - Outgoing messages contain a digital signature verifying `(channelId + ciphertext + iv + deviceId)`, preventing sender impersonation and payload tampering.
- **Media & Photo Sharing**:
  - Uploaded photos are validated for MIME type and binary header magic bytes (PNG, JPEG, GIF, WEBP) client-side before encryption.
  - Encrypted media payloads are stored as ciphertext in PostgreSQL and decrypted into Blob URLs on recipient browsers.

## Non-Functional Requirements & Architecture

### 1. Stack & Infrastructure
- **Backend Framework**: Node.js and Express with modular routing (`src/server/routes/channels.js`, `src/server/routes/profile.js`).
- **Real-Time Layer**: Socket.io over WebSockets for instant messaging, join requests, approval broadcasts, and closure events.
- **Database & ORM**: PostgreSQL database on `192.168.1.109:5432` managed via Prisma ORM. All database tables are prepended with `tbl_chatapp_` (`tbl_chatapp_channels`, `tbl_chatapp_channel_members`, `tbl_chatapp_messages`, `tbl_chatapp_invites`, `tbl_chatapp_profiles`).
- **Security & Rate Limiting**: Express endpoints protected with `helmet` security headers and `express-rate-limit` (global and route-specific limits).
- **Deployment**: Self-hosted, Docker-ready, runnable locally via `node src/server/app.js`.

## High-Level API Reference

### REST Endpoints (`/api/channels`, `/api/profile`)
- `POST /api/channels/join`: Register/verify membership in channel (handles pending approval and single-use invite validation).
- `GET /api/channels/my-channels?deviceId=...`: Fetch list of active channels for a device ID.
- `GET /api/channels/:channelId/messages?deviceId=...`: Fetch historical encrypted messages for active members.
- `GET /api/channels/:channelId/members?deviceId=...`: Fetch list of active channel members.
- `GET /api/channels/:channelId/pending-members?ownerDeviceId=...`: Fetch pending join requests (Owner only).
- `POST /api/channels/create-invite`: Generate a single-use invite PIN `INV-XXXXXX` (Owner only). Block reactivation of consumed PINs.
- `POST /api/channels/approve-member`: Approve a pending join request (Owner only).
- `POST /api/channels/deny-member`: Deny a pending join request (Owner only).
- `POST /api/channels/leave`: User leaves or owner permanently closes/deletes channel.
- `POST /api/channels/kick`: Owner permanently kicks a target device.
- `POST /api/profile/save`: Save friendly display name server-side by `deviceId`.
- `GET /api/profile/:deviceId`: Retrieve stored friendly display name.

### Socket.io Events
- Client -> Server: `join_channel`, `send_message`, `request_join`, `approve_user`, `deny_user`, `leave_channel`, `kick_user`.
- Server -> Client: `new_message`, `member_status_changed`, `pending_join_request`, `you_were_approved`, `you_were_denied`, `user_kicked`, `you_were_kicked`, `user_left`, `channel_closed`.
