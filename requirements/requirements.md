## Functional Requirements

### 1. User Identity & Authentication
- **12-Word Identity Phrase**: When a user visits the application, they can choose between "I'm New" or "Returning User".
  - If new, the 12-word seed phrase is generated **strictly server-side** using Node.js CSPRNG (`crypto.randomBytes`) selected from the standard BIP-39 2,048-word dictionary ($2^{132}$ entropy combinations).
  - **Server-Side Collision Check**: The server hashes the candidate phrase to `deviceId` and checks PostgreSQL (`tbl_chatapp_profiles`) to guarantee global uniqueness. If a collision occurs, it silently regenerates.
  - **Timing Attack Mitigation**: Every generation response includes a randomized 50–200ms delay so an attacker cannot deduce collision retries.
  - **Zero Client Generation**: Client-side wordlists and phrase generators are completely removed. Zero client fallbacks are permitted.
  - Returning users enter their 12-word phrase to unlock their cryptographic identity and device identity.
  - Losing the 12-word phrase results in permanent loss of identity and channel access keys.
- **Client Device ID & Server-Side Profile Persistence**:
  - Each device derives a unique, non-identifiable Device UUID client-side from the 12-word seed (`deriveDeviceId`).
  - Custom friendly display names are saved server-side per `deviceId` (`tbl_chatapp_profiles`) and automatically restored when returning users log in.
- **Session Persistence Control**:
  - Users can select their session security preference on login:
    - **Remember me on this device (7-day persistence)**: Saved in `localStorage`.
    - **Session only (expires on browser close)**: Saved in `sessionStorage`.

### 2. Private Server Mode & Admin Control Center (/admin)
- **Configurable Server Privacy Mode**:
  - Controlled via environment variable `PRIVATE_SERVER` (`"true"` | `"false"`).
  - When `PRIVATE_SERVER="true"`, user identity phrase generation and device registration require a valid **Server Invite Token** generated by the server admin.
- **Alphanumeric Admin Key Security Constraint**:
  - Requiring `PRIVATE_SERVER_KEY` in `.env` to be an alphanumeric string of **minimum 32 characters**. Server startup aborts if this rule is violated.
- **Admin Control Web Interface (`/admin`)**:
  - Accessible via `/admin` (served by `src/client/admin.html`).
  - Authenticates admins via `POST /api/admin/login` protected with heavy rate limiting (5 attempts limit per 15 minutes to block brute-forcing).
  - **Token Generator**: Admin can generate **1-Time Use** or **Forever Tokens**, with optional custom token strings (e.g. `SRV-TEAM123`).
  - **Metrics Summary**: Real-time stats for Total Tokens Created, Active Tokens, Revoked/Invalidated Tokens, and Forever Tokens.
  - **Token Management Table**: Displays Token Code, Type (1-Time vs Forever), Status (Active, Consumed, Revoked), Used By (Device ID & Friendly Name), Usage Count, and Created At.
  - **Emergency Token Revocation**: Admin can instantly invalidate/revoke any token (1-time or forever) to immediately sever access.

### 3. Channel Creation & Access Control
- **6-Word Channel Key**: Channels are identified and encrypted via a 6-word phrase key generated **strictly server-side** with DB uniqueness validation (`tbl_chatapp_channels`).
- **Standardized UI Terminology**: All UI elements strictly use uniform terminology: **12-Word Identity Phrase**, **6-Word Channel Key**, and **One-Time Invite PIN**.
- **Auto-Generated & Custom One-Time Invite PINs**:
  - Creating a new channel auto-populates an initial **One-Time Invite PIN** (`INV-XXXXXX`) while supporting custom PIN entries (e.g. `tester123`).
  - Joining an existing channel requires entering the 6-word channel key AND a valid **One-Time Invite PIN** generated by the channel owner.
- **Global OTP Non-Reuse Security Hardening**:
  - Once used, the invite PIN is permanently marked as consumed in PostgreSQL (`is_used = true`).
  - Consumed OTPs can NEVER be reused or reactivated by channel owners or kicked members under new identities.
- **Global Notification Center & Toast System**:
  - Replaces native browser popups with a fixed-position global Notification Bell (`#btn-notification-bell`) and real-time unread badge counter (`#notification-unread-badge`) accessible on all screens.
  - Non-blocking bottom-right toast notifications (`#toast-container`) alert users to join approvals, member events, and action statuses.
- **Custom In-App Modals**:
  - Native browser `confirm()`, `alert()`, and `prompt()` popups are completely replaced with custom glassmorphism in-app modals (`#modal-confirm`, `#modal-prompt`).
- **Owner Join Approval Queue & Auto-Join**:
  - Channels default to "Owner Approval Required".
  - Non-owner joiners enter a `pending` state until the channel owner explicitly approves their join request.
  - Upon approval, non-owner joiners receive a real-time `you_were_approved` socket event and are **automatically navigated into the channel chat window**.
  - `pending` users are strictly blocked from fetching chat history or receiving real-time socket broadcasts.
- **Friendly Display Names in Member List**:
  - Member lists in the channel UI display real friendly display names (e.g. `You (Alice)`) instead of raw Device IDs.
- **Owner Channel Closure & Deletion**:
  - When a channel owner leaves or closes a channel, the channel is permanently deleted from the database.
  - All stored historical ciphertexts and member records are cascaded and wiped.
- **Kicked & Left Member Access Prohibition**:
  - Once a user leaves or is kicked from a channel, they are permanently prohibited from re-joining or querying historical messages.

### 4. End-to-End Encryption & Messaging
- **Client-Side E2EE & Fixed Height Layout**: All text messages and photo uploads are encrypted client-side using Web Crypto API (`AES-256-GCM` + 12-byte random IV) prior to transmission. The chat window maintains a stable fixed-height container area (`85vh` / `720px`).
- **Digital Signatures (Impersonation Protection)**:
  - Every device derives an **ECDSA (P-256)** digital signing keypair client-side.
  - Outgoing messages contain a digital signature verifying `(channelId + ciphertext + iv + deviceId)`, preventing sender impersonation and payload tampering.
